# Alloy Connector — что видит и чем управляет пользователь после подключения

## 1. Целевой пользователь
Compliance/Risk менеджер в fintech-компании или банке, использующий Alloy для
онбординга клиентов (KYC/KYB) и мониторинга мошенничества.

## 2. Момент истины после подключения
Сразу после `connect_alloy` — сводка по очереди решений (evaluations): сколько заявок
ожидает ручного review (не прошли автоматически ни approve, ни deny).

## 3. Что пользователь видит
- Заявки на онбординг (entities) и их статус решения (approved/denied/manual review) —
  `list_entities`, `get_entity`.
- Полный результат оценки риска (evaluation) с сработавшими правилами — `get_evaluation`.
- Очередь заявок, требующих ручного решения комплаенс-офицера — `list_review_queue`.
- Историю документов, поданных для верификации (ID, адрес) — `list_documents`.
- Журнал действий по заявке (кто и когда принял решение) — `get_entity_audit_log`.
- Настроенные workflow-политики принятия решений — `list_workflows`.

## 4. Чем пользователь может управлять
- Принимать ручное решение по заявке в очереди review — `submit_manual_decision`
  (approve/deny с указанием причины).
- Запрашивать дополнительный документ у клиента — `request_document`.
- Повторно запускать оценку риска с обновлёнными данными — `re_run_evaluation`.
- Добавлять заметку комплаенс-офицера к делу — `add_case_note`.
- Помечать сущность как подозрительную для дальнейшего расследования (SAR-триггер) —
  `flag_entity`.

## 5. "Вау"-момент для демо потенциальному клиенту
"Смотри — говорю Webbee: 'сколько заявок ждёт моего ручного решения прямо сейчас?'. Она
находит через `list_review_queue`, показывает, какое именно правило сработало (`get_
evaluation`), а я принимаю решение — `submit_manual_decision` фиксирует его с полным
аудиторским следом для регулятора."

## 6. Что делает это "заточенным под него"
`list_workflows` отражает РЕАЛЬНЫЕ правила риска, которые именно эта компания настроила
под свою юрисдикцию и продукт — не универсальный чек-лист KYC.
